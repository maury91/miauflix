# Miauflix Detailed Changelog

Every change in full, for developers and self-hosters. The short version for users is in [CHANGELOG.md](CHANGELOG.md).

## Unreleased

### Features

- TV remuxes, Phase 1 of [the TV remux plan](docs/plans/tv-remux-plan.md). media-load builds a remux of a stored file for AVPlay as MPEG-TS HLS: the video is copied, each audio language keeps one track (a TV-decodable one, `aac`/`ac3`/`mp3` copied and `eac3` converted; otherwise the one with the most channels converted; converted tracks are AC-3, 640 kbit/s at 5.1, 448 kbit/s for 3 to 5 channels, 192 kbit/s at stereo or mono), and every subtitle track becomes a sidecar: text as WebVTT (`s<N>.vtt`), ASS/SSA as one-track Matroska with the attachments (`s<N>.mkv`), PGS as `.sup`, DVD/DVB as Matroska. FFmpeg runs one remux at a time with `-threads 1` at niceness 19 (0 for a viewer waiting; raising a running remux's priority needs `CAP_SYS_NICE`, so as the `bunqueue` user it keeps 19), reads the source over a loopback HTTP server (`streamFile`, speculative) and uploads segments, playlist and sidecars back to it with `PUT`. Each upload is encrypted whole (AES-256-GCM, the host key) under `<storage location>/remux/<id>/<keyed name>`, so allocation measurement and storage removal cover it. Migration 4 adds `remux` (encrypted path and plan, priority, state, ready seconds, bytes; cascades with `storage`) and `remux_file` (name, kind, segment order and length, encrypted sidecar track details). The served playlist is built from stored segments only (`EVENT`, closed once complete), so a remux plays while it is built. A remux is complete when the playlist was closed, every sidecar arrived, and its length is within 1.5 s of the plan; otherwise its files are deleted and it is `failed` (a new request queues it again). Remuxes left running by a restart are rebuilt; a queued remux waits for its file to finish downloading; a `watching` request stops a lower-priority running remux, which runs again afterwards. Tested on a 2020 Tizen 5.5 TV, AVPlay never finishes preparing fMP4 HLS (any codec, H.264 with AAC included) and ignores E-AC-3 in MPEG-TS (DVB and ATSC stream types alike), while MPEG-TS with HEVC 10-bit and AC-3 or AAC plays: hence MPEG-TS and AC-3. Migration 5 fails the remuxes built earlier as fMP4 so the next request rebuilds them, deleting their files. Contract `media-load` 1.2 adds `requestRemux`, `remuxStatus`, `remuxChanged` and `readRemux` (`since: 2`). FFmpeg uploads a playlist before the segment it adds and exits without waiting for its last uploads, so segments are placed when both are stored and a finished job waits up to 5 s for late uploads. Playlist and segment uploads are stored in the order they arrived; sidecar uploads, which stay open for the whole run, are stored on their own (queued with the rest, they held every segment back in memory until FFmpeg ended, so nothing was playable before the remux was complete). The loopback server has no idle timeout: FFmpeg streams each sidecar as one upload for the whole run, and a PGS track can send nothing for minutes (with Bun's timeout the `.sup` upload was cut and the remux failed). The `miauflix-media-load` image now runs on Debian (`oven/bun:1.4.0`, FFmpeg 7.1 from apt, its production dependencies installed there so native packages get glibc binaries, `gosu` standing in for `su-exec`, same `bunqueue` uid 1001): Alpine's FFmpeg (6.1 and 9.0 alike) decoded TrueHD 8 to 9 times slower (42 s against 4.5 s for two minutes of 5.1), holding a TrueHD remux at about 3x real time instead of 19x (MobLand S01E01: 189 s for 59 min). `@thaunknown/utp-native`, whose prebuilt binary needs glibc, now loads too. The all-in-one `miauflix-services` image stays on Alpine (bunqueue needs it) and gets Alpine's FFmpeg, so its remuxes of TrueHD files are slower.
- Backend: `TvRemuxService` plans a remux from the stored probe (`remuxPlan`, which now also records the `forced` and `hearing_impaired` dispositions) and requests it. AVPlay sends `playsRemux: true`. A session whose file needs converted audio plays its remux instead when one is complete or built at least a minute past the resume point (`remuxPlayable`, delivery mode `remux`, stream URL `/api/stream/:token/remux/index.m3u8`, audio tracks those of the remux), before any search for another source; otherwise it asks for a remux at `watching` priority, converts meanwhile, and gets `recreate` once the remux is complete or, while it is built, a minute past the viewer's saved position (checked on every `remuxChanged` progress event, at most one check at a time per session). `GET /api/stream/:token/remux/:name` serves the playlist, segments and sidecars (names validated, `Range` forwarded, 600 requests a minute). `POST /:token/prefetch?remux=true` (sent by AVPlay for the next episode) requests a `next` remux once the file is downloaded, checked every minute for 3 hours. The player uses the delivery's duration for a remux and switches its tracks in AVPlay. AVPlay plays a playlist without `#EXT-X-ENDLIST` as a live stream: it reports no duration and starts near the newest segment, so `AvplayMedia.open` takes the delivery's duration in that case, seeks to the requested start (0 included, unless a resume already seeked), and starts playing only once that seek has landed (playing first showed a few seconds from near the newest segment). The switch from converted audio keeps the picture: on `recreate` while converting on a TV, `usePlaybackSource` keeps showing the current session until the new one arrives (`restartSession(keepPicture)`), converted audio stops with `keepPicture` (the `<video>` paused on its last frame instead of emptied), and the paused `<video>` stays above AVPlay, without media events, while AVPlay opens, seeks to the `<video>`'s exact time and plays; AVPlay's picture replaces the frame as it plays, and the `<video>` goes on `playing`, on `error` or after 15 s. Checked on Tizen 5.5: a paused MSE `<video>` keeps its frame while AVPlay prepares (a 0.2 s black flash), a canvas copy of it is black (video is a hardware plane), and a second AVPlay (`webapis.avplaystore.getPlayer()`) takes the decoder from the first as soon as it prepares, so it cannot preload in the background. A `recreate` no longer rebuilds the session object, which restarted converted audio needlessly. AVPlay ignores `EXT-X-START` and opens an unfinished playlist three segments before its end, downloading those first: on a switch it showed a frame from near the newest segment and took about 5 s. The player now opens a remux playlist with `?start=<seconds>` (the held picture's time, else the resume point, else 0), and the backend serves each streaming key's playlist cut two segments past the one at that time until it asks for its first segment (AVPlay reads the playlist twice as it opens and starts from the second; over the internet the second read can come seconds later) (`playlistStartingAt`; a finished playlist, or a start past the listed segments, is served whole), so AVPlay starts there and fetches only what it plays; reloads get the whole playlist. AVPlay then buffers one second, not its default three segments (about 15 MB), before it plays an HLS playlist and after it runs dry (`setBufferingParam` `PLAYER_BUFFER_FOR_PLAY` and `PLAYER_BUFFER_FOR_RESUME`, 1 s): on Tizen 5.5, with segments arriving in 1.5 s each, the start plus a seek went from 6.8 s to 3 s. Torrent streams keep the default. A TV version opens at its start (`AvplayMedia.open`'s `startSeconds`: the held `<video>` time on a switch, else the resume position): AVPlay is seeked in its idle state, before `prepareAsync`, so it prepares there (tested on Tizen 5.5: prepared within a second of a 123 s target, one segment fetched, playing 1.5 s after opening). Preparing first and seeking after showed a frame from the start of the segment before the seek, and cost about 2 s more. The resume seek that follows to the same place (within 1.5 s) is skipped; an AVPlay that refuses an idle seek seeks once prepared, as before. Tested on Tizen 5.5: such a playlist plays on while it grows, seeks within the listed segments, and a seek past the last one lands on it.
- TV remux hardening (review of the remux PR): a remux replaces converted audio only when the video is not converted too (`remuxReplaces`: the remux copies the video, which a client that needed it converted cannot decode). A session waiting for its remux is checked again after a media-load event gap (`onRemuxChanged`'s `onResync`, `TvRemuxService.status`), a status heard while the previous one was being checked is checked after it instead of being dropped, and the check made when a probe finishes uses the viewer's saved position. media-load: a remux stopped while its directory is prepared no longer starts FFmpeg, a clean exit waits for the closing playlist before verifying, and `close()` waits for the stopped remux to be put back in the queue before the database closes. Frontend: a `recreate` no longer undoes the delivery before it (`playbackDelivered` in the realtime slice), a TV version waits for the saved progress before opening (its `start` is fixed per stream), AVPlay's early seek gets callbacks and seeks after preparing when it fails, an audio track chosen while paused is switched on play (AVPlay switches audio only while playing), and the codec report is left out when every query of a kind throws.
- A remux reserves its room before FFmpeg starts: `StorageService.reserveAdditional` raises the source's reservation by the file's size plus 5% (`REMUX_SIZE_RATIO`) on top of what it holds, evicting weaker storage first (retained rank for a `watching` remux, speculative rank and the playback reserve kept otherwise) and rejecting when the storage limit or the filesystem has no room, which fails the remux before anything is written. When the remux ends (complete, failed or stopped) the storage is measured, and the reservation goes back to what it was unless a download raised it meanwhile. Session sources are also filtered by the video codecs a TV reports (`filterVideoCodecSources`, ffprobe names mapped from the release's codec): a release whose video the TV does not decode, such as AV1 on a TV without it, is no longer picked, since nothing converts it. HEVC stays with `allowHevc`, as it can be converted. Clients that report no codecs are unaffected.
- Media versions: a new `media_variant` table (schema migration `AddMediaVariant`) records each playable version of a source's file apart, `original` or `remux`, with its state (`building` while queued or written, then `ready`), container, video codec and audio codecs (ffprobe names; the path encrypted like `media_probe`'s). An original is recorded whenever a probe is stored, and the data migration `backfillMediaVariants` records one for every stored probe. A TV version is recorded when `TvRemuxService` requests or finds it (its codecs from the plan: the video as it is, each kept track copied or `ac3`, `mpegts`), follows media-load's events (`ready` once complete, removed once failed), and is recorded from the stored probe when media-load reports one this backend did not request. A source whose file has a TV version the client plays (`TvRemuxService.usable`, `codecsPlayable`), built or still being built, is no longer swapped for another release because its own audio needs conversion: when the session starts, when an alternative is looked for, and when a background probe finishes. It plays the TV version, or converts until the TV version is built past the viewer and then switches. `schema-upgrade.test.ts` now builds its legacy database without the tables later migrations add.
- TV remux review, second pass. media-load: a remux's room is held in its own column (`remuxReservedBytes`, migration 6; the charge is the largest of allocation, download reservation and remux room), so a download reserving while a remux runs keeps its share; the storage is measured before reserving, after an earlier run's leftovers are deleted, so they are not charged next to their replacement; the estimate adds every converted track at its AC-3 bitrate (`ac3Layout`) on top of the source file; when the storage cannot be measured afterwards it stays charged the room the remux held. A remux is complete only when every segment the closing playlist lists is stored, and none starts after a shutdown began while its file was being checked. Backend: a probe and its original version are written in one transaction; a shortened playlist drops the upstream `Content-Length`, `Content-Range`, `Content-Encoding` and `ETag`; a remux is chosen (and waited for) only when the client decodes its codecs, and the resume point it is checked against is worked out from the delivery finally chosen, after a source switch; a session waiting for its remux checks it again once registered, in case it finished meanwhile; the search for a release that needs no conversion goes past one whose file cannot be resolved; a file's TV version is recorded in order, so a failure is not overwritten by an earlier status. Frontend: AVPlay's length for an HLS playlist is taken as partial when more than 5 s short of the file's, which then stands.
- TV remux review, third pass. media-load: a remux's room is added to everything its storage is committed to (`MAX(allocatedBytes, reservedBytes) + remuxReservedBytes`), so a pack still downloading keeps room for the rest of its files and the remux; while the remux writes, its output counts twice until its room goes, an overcount. Backend: the original version is recorded from the probe kept, so a second, different report for the same file cannot replace its codecs; a playlist being shortened is read whole, whatever range was asked for. Frontend: when AVPlay reports the opening seek failed, a seek asked for since stands; an audio track whose switch failed on play is no longer marked selected, so it can be asked for again.

### Bug fixes

- Samsung TVs no longer jump every few seconds while audio is converted: the stall watchdog took a moving playhead with no newly decoded frame for 1 s as a frozen picture and seeked in place (`frozen-seek`), but Tizen 5.5 updates `getVideoPlaybackQuality().totalVideoFrames` in batches of about 48 frames (2 s at 24 fps). A frozen picture now needs 5 s without a new frame.
- The backend crashed on startup when `CSP_IMAGE_ORIGINS` was unset: configuration transforms do not run on empty values, so `get('CSP_IMAGE_ORIGINS')` returned `''`, which `?? []` let through, and `cspOrigins` called `.map` on it. `createRoutes` now uses `|| []`.
- media-catalog piled up catalog instances. `CatalogRuntime`'s `activate`, run every time the backend pushes its configuration (each time it connects), built a new `CatalogService` and replaced `ctx.catalog` without stopping the previous one, whose artwork pump, artwork worker thread and background timers kept running. A backend in a restart loop left dozens running in one process: the main thread stayed at 100% CPU, HTTP requests timed out (the backend reported the catalog unavailable) and Bunqueue jobs lost their locks (`Job not found or not in processing state`). `CatalogRuntime` now keeps a single active instance: activation retires the previous one (`stopArtworkBackground`) before installing the next, a rejected configuration leaves the active one serving, and activate, deactivate and stop run one at a time on the runtime's own chain, even for callers that bypass `ServiceConfiguration`'s queue. Testing a configuration only builds a provider. Artwork subscribers are held by the runtime and shared by every instance (`ArtworkSelectionService` takes the set), so the host's `artwork` subscription, made once while the service is ready, keeps receiving updates after a configuration push replaces the instance. A replaced instance is retired for good: a database artwork scan still waiting on a provider request when it is replaced stops instead of resuming, drops the metadata it fetched with the old configuration, and its `ArtworkSelectionService` rejects enqueues and publications, so in-flight work cannot overwrite artwork state or announce it to the shared subscribers. Retirement also cancels the instance's queued background backdrop-focus analyses and refuses new ones (`BackdropFocusService.stopBackground`; running analyses and requests it is still serving finish), so a replaced instance's queue no longer runs alongside the new one's. Cancelled tasks leave the in-flight map at once, so an `ensure` for the same image schedules a fresh analysis instead of receiving the cancellation (the map's cleanup only removes an entry that still belongs to its own task). If the replaced instance fails to shut down, the activation still succeeds and the failure is logged: the replacement is already serving, and reporting failure made the configuration activate yet another instance with the previous values. `ctx.catalog` is never null during a replacement (the new instance is installed in the same step the old one is retired, only the old one's worker-thread shutdown is awaited afterwards), and deactivation and stop drain the queue workers before detaching it: a Bunqueue job that found no catalog was acknowledged without running. sources, media-load and list-service were checked: none builds a new instance on activation.
- Logos the artwork worker cannot download (TMDB's SVG logos; only PNG is analyzed) were recorded as failed and retried every hour forever, republishing the title's artwork each time. The shared `isAnalyzableArtworkUrl` (`services/artwork-urls.ts`, also used by the worker) now lets `ArtworkSelectionService` skip them for good, and failures already recorded for them no longer schedule retries.
- Login could be brute-forced and leaked which accounts exist. The only limit was 1 request per second per IP (about 86 000 guesses a day from one address, more from several), `POST /api/auth/users` accepted 1-character passwords, and `validateUser` returned at once for an unknown email but ran bcrypt for a known one. New `LoginThrottle` (`services/auth/login-throttle.ts`, in memory): after 10 failures within 15 minutes of the first, `POST /api/auth/login` answers 429 with `Retry-After` for that account (any IP, even with the right password) until the window ends, and logs a suspicious-activity audit event; a successful login clears it. Each attempt is reserved (`begin`) before the password is checked and settled afterwards (`fail`, `succeed`, or `release` on an error), so failures plus attempts in flight never pass 10: concurrent requests from many addresses can't all get past the check before any failure is counted (while 10 are in flight the next one gets a 1-second `Retry-After`). The map holds at most 10 000 accounts, kept in window order so expired entries are dropped from its front without scanning it. Only expired entries make room: an active block is never dropped for a new email, and while the map is full of active entries, accounts not tracked yet get a `Retry-After` until the oldest window ends (filling it can delay other logins, but never lifts a block). Someone who knows an email can keep that account locked this way, which is the trade-off of a per-account limit. `POST /api/auth/users` requires 8 characters, like setup. An unknown email is checked against a dummy bcrypt hash, so both paths cost the same.
- A replayed refresh token was only refused. The reuse branch of `refreshTokens` fired only when two rotations raced, so a stolen token that had already been rotated got a 401 and nothing else. `refresh_tokens` gains `previousTokenHash` and `rotatedAt` (nullable, added by schema sync), set on each rotation. When a session's previous token is presented (refresh, logout, session listing), more than `REFRESH_REUSE_GRACE_MS` (30 s) after the rotation, the session is deleted and a critical `SUSPICIOUS_ACTIVITY` event is logged; within the grace it is only refused, since concurrent refreshes from two tabs look the same.
- Access tokens and realtime sockets outlived their session. Access JWTs were trusted for their 15 minutes without a database check, were not tied to a session (`X-Session-Id` was taken from the client as is), and carried the role they were issued with; the WebSocket checked the token once at connect. Access tokens now carry `sid`. New `AuthService.authenticateAccessToken(token, sessionId)` requires `sid` to match the session the token is sent for and the session's refresh token to exist and not be expired (`resolveSession`, cached for `SESSION_CHECK_TTL_MS`, 5 s), and takes the email and role from the user row; the auth middleware and the realtime `authenticate` message use it. Tokens without `sid` are refused, so clients refresh once after the update. `AuthService.onSessionRevoked` reports logout, `revokeSession`, refresh-token reuse, expiry clean-up and device-slot eviction (`deleteOldestByUser` now returns the evicted session), always naming the session, and clears its cache entry; lookups still in flight are tracked apart from the cache (whose entry may have been replaced or swept meanwhile) and resolve to no session once it is revoked, so they can't let a token or socket through. The realtime gateway closes the revoked session's sockets at once (`1008 Session ended`), and rechecks every socket each minute, which also updates its admin flag. The e2e compose files raise `MAX_DEVICE_SLOTS_PER_USER` to 20 (its maximum): every test file logs in as the same admin in parallel, and with 5 slots the evicted sessions' access tokens now stop working mid-test.
- Smaller hardening:
  - Request bodies under `/api` are capped at 256 KiB (413 above it); the avatar upload keeps its own 1 MiB limit. Before, only the avatar route had a limit, and other endpoints, unauthenticated ones included, accepted whatever Bun allows by default.
  - New `SERVICE_TOKEN`: the backend presents it on every connection to the services (`RemoteService`, read through `ConfigurationService`), and the four services require it when it is set (the contract's `token` option). Without it, anyone reaching a service's port could use it and replace the `ticketKey` that signs `bytes` URLs. `docker-compose.yml` passes `SERVICE_TOKEN` to the backend and every service container. The services still listen on `0.0.0.0` by default, which their images rely on; the environment variable docs now say to set the token or `*_HOST=127.0.0.1` when running them natively, and that the token crosses the network unencrypted unless the service URL is `https://`.
  - `QrLoginService.create` stored the raw first `X-Forwarded-For` value as the requester's IP; it now uses `getRealClientIp`, which trusts the header only with the reverse proxy's secret.
  - The stream route logged failures with `console.error`, bypassing the logger's redaction; it uses `logger.error` now.
  - Streaming keys were cached for 90% of `STREAM_TOKEN_EXPIRATION` from their last verification, so a key verified shortly before it expired kept working for most of another lifetime. The cache entry now expires with the key.
  - `flaresolverr` is pinned to `v3.5.2` and `jaeger` (`jaegertracing/all-in-one`) to `1.76.0`, instead of `latest`.
- `hono` is updated from 4.10.6 to 4.13.18 (backend, frontend, backend-e2e) and `typeorm` from 0.3.27 to 0.3.31, for published advisories: among them arbitrary file access through `serveStatic` (which serves the web app), a `bodyLimit()` bypass with chunked bodies (used on avatar uploads) and cookie parsing and writing issues. `bun.lock` was also out of date (it still listed removed packages) and is regenerated.
- The audit log stored live secrets. It redacted only `Authorization`, `Cookie` and `X-Reverse-Proxy-Secret`, and kept every other header, the full query and the path, so the TV app's `X-Refresh-Token` / `X-Refresh-Tokens`, stream tokens (`/api/stream/<token>`), QR approval tokens (`/api/auth/qr/<approvalToken>`) and `?streamingKey=` were written to `audit_logs` as they were, undoing the hashing in `refresh_tokens`. New `utils/redact.util.ts`: only an allowlist of headers is kept (`accept`, `content-type`, `host`, `origin`, `referer`, `user-agent`, `x-forwarded-*`, `x-session-id`, `sec-fetch-*` and a few more), the token segment of stream and QR paths becomes `REDACTED` (in the description, `metadata.path` and the trace span too), and query values whose key looks like a secret (`token`, `key`, `secret`, `password`, `code`, `sig`) are masked, also inside `Referer`. Paths are decoded the way Hono's router decodes them before matching, so `/api/%73tream/<token>` is masked too, and the web app's QR approval page (`/auth/qr/<approvalToken>`, seen in `Referer`) is covered. Traces had the same leak: the request span's `url.full` held the full URL, written to the trace files and sent to the OTLP endpoint when one is set. A span processor registered before the exporters now masks `url.full`, `http.url`, `http.target`, `url.path` and `url.query` the same way (`instrumentation/redact-url-attributes.ts`). Rows already in the database are not rewritten.
- Script on the web app's page could read refresh tokens. With `X-Auth-Transport: token`, login, setup, refresh and QR claim returned the tokens in the body even when the refresh token came from the HttpOnly cookie, so an XSS could call `/api/auth/refresh/:session` and receive a fresh refresh token, logging the real user out and keeping the session for up to 30 days. `wantsTokenTransport` now takes the session cookie prefixes (`AuthService.getSessionCookiePrefixes`) and refuses token transport to a request that carries any `<refresh cookie>_*` or `<access cookie>_*` cookie; the backend sets cookies instead. The TV app, which sends no cookies, is unaffected.
- No security headers were set. The backend now uses Hono's `secureHeaders` on every response (`middleware/security-headers.middleware.ts`): `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: same-origin`, `Cross-Origin-Opener-Policy: same-origin` and a Content Security Policy written for the served web app: `default-src 'self'`; scripts from `'self'`, `'wasm-unsafe-eval'` (the subtitle renderer) and the SHA-256 of each inline `<script>` in `FRONTEND_DIR/index.html`, read at startup (no `'unsafe-inline'` for scripts; the closing-tag match also accepts `</script >`, as CodeQL flagged); `'unsafe-inline'` styles (styled-components); images from `'self'`, `data:`, `blob:` and `image.tmdb.org`; `blob:` media and workers; `object-src 'none'`; artwork origins besides TMDB's from the new `CSP_IMAGE_ORIGINS` (bare `http(s)` origins only, anything else is ignored with a warning; the E2E compose files set it to the TMDB image mock, whose blocked backdrops failed the home hero test); `frame-ancestors 'none'`. `Cross-Origin-Resource-Policy` is not set, since the TV app loads streams and images from its `file://` page, and HSTS is left to the TLS terminator: the Caddyfile now sends `Strict-Transport-Security: max-age=31536000` (without `includeSubDomains`).
- media-load's encrypted chunk store reused its AES-256-CTR keystream. Every store used `SOURCE_SECURITY_KEY` itself, and the counter block held only the piece index. So piece N of every download was encrypted with the same keystream, and because CTR counts once per 16-byte block, piece N+1's keystream was piece N's shifted by one block. With one known plaintext (the content is public), someone holding a copy of the disk could recover the keystream and decrypt the other downloads without the key.
- Names on disk could be matched to torrents. A storage's directory was `sha256(infohash + DOWNLOAD_SALT)`, and `DOWNLOAD_SALT` defaults to a fixed string published in the repository. File names were `sha256(name + key + "download-" + infohash)`. Info hashes are public on indexers and the DHT, so anyone holding the disk could test candidate torrents: the directories needed no secret at all, the file names only the key on the same machine. Version 1 file names also used only the base name, so files sharing a name in different folders of one torrent (`S01/info.nfo`, `S02/info.nfo`) shared one encrypted file.
- Chunk encryption is now versioned, and version 2 is used for every new download. Each store gets two random 32-byte values, kept in its encrypted layout in media-load's database: `contentSalt` and `filenameSalt`. The content key is `HMAC-SHA256(key, "miauflix-chunk-store-v2-content:" + contentSalt)`. File names are `HMAC-SHA256(key, "miauflix-chunk-store-v2-name:" + filenameSalt + "\0" + full path)`, cut to 24 hex characters. The counter block is the chunk's byte offset in 16-byte blocks, so a store is one continuous keystream; chunks that start mid-block continue that block's keystream. New storage directories are 16 random hex characters (the format storage import accepts). Neither the info hash nor anything derived from it appears in a key or a name, so the files on disk can only be tied to torrents through the layout. That is the step toward keeping those salts off the machine.
- Version 1 is kept, unchanged, to read what is already on disk. `EncryptedStorageLayout` gains optional `encryptionVersion` and `contentSalt`; a layout without a version means 1, so existing downloads keep working without migration, and a storage keeps the `location` recorded when it was created. `storeEncryptionOptions` opens a store at the version and salts its saved layout records; a storage without a layout uses version 1 if it has verified pieces (data from before layouts) and new random version 2 salts otherwise. The live store exposes its salts, and layouts built from a running torrent copy them. `updateEncryptedLayout` never replaces a saved layout, and the version 1 salt correction (`download-<source hash>`) skips version 2 layouts, so a store's salts cannot change. `EncryptedChunkStore` requires `encryptionVersion`, and refuses version 2 without both salts; opening a version 2 layout without its `contentSalt` fails instead of guessing. `DOWNLOAD_SALT` is no longer read: it stays in the schema so existing configurations load, and its description says it is unused. Existing downloads stay on version 1 until they are deleted; re-encrypting them is not done.
- File sizes on disk could identify torrents: CTR keeps the exact length, and a torrent's file sizes are close to unique, so random names and keys alone did not stop a scanner holding a list of known sizes. New media-load setting `STORAGE_PAD_FILE_SIZES` (boolean, advanced, default `true`; an empty or missing value also counts as on, so a host that leaves it out does not drop the padding) pads version 2 files with Padmé (`paddedLength`): the length is rounded up so about log2(log2(length)) significant bits remain, at most 2^-5 (3.1%) larger above 64 KiB and 2^-6 from 4 GiB, and files up to 64 KiB take 64 KiB. Between 700 and 800 MiB, over 25 000 exact sizes become at most 8. A file is padded when the store first opens it, before any data is written, so its size never shows the exact length mid-download (players fetch a file's tail early). The padding is random bytes rather than a hole, so a complete file's allocated blocks do not show the length either; data never reaches it, since chunks stop at the file's length. While a download is incomplete, though, the not-yet-written data range is a hole on sparse filesystems, and the allocated padding starts at the original length, so the extent map (`SEEK_HOLE`, `FIEMAP`) can show that length until the data around it is written. The store takes it as `padFiles` (read when a torrent is added) and records nothing: padding never changes what is read, so the setting can be switched either way. Turning it on pads an existing version 2 download's files the next time its torrent is added (resumed, seeded again or re-downloaded); files only read from disk are not padded. Version 1 files are never padded. A file now spans its padded size from the start, so reading a never-written chunk returns undecryptable bytes instead of failing past the end of the file; callers already check the bitfield before reading, as in-range holes of partial files always behaved this way. Storage reservations count padded sizes while the setting is on (layouts without a version are assumed padded, since a new download's `.torrent` has none), and disk usage was already measured from allocated blocks. What remains visible on disk: how many files a download has, their rounded sizes, and (mid-download, on sparse filesystems) the original length through the extent map. Media-load's database keeps exact file lengths and offsets, piece length and total size unencrypted, so it must be protected like the rest of the link from files to torrents.

- Every request waited on a database insert. The audit middleware runs before rate limiting and auth and awaited `AuditLogService.logSecurityEvent`, whose `save` goes through `Database.write`, the single lane shared with every transaction; so each request, every video range request and unauthenticated floods included, waited behind whatever transaction was running. Locally about 94% of `audit_logs` rows were plain `API_ACCESS`. `logSecurityEvent` now queues the row (stamped with the event time, its metadata copied as plain JSON so one unserializable value, such as a circular reference or a BigInt, can't fail the whole batch; such metadata is replaced with the error and the path) and returns; the queue is written as one multi-row `INSERT` (`AuditLogRepository.insertMany`) 1 s after the first event or as soon as 200 are queued, one flush at a time. The batch being written is held apart from the queue: a failed write puts it back at the front and retries it 5 s later (that timer replaces a shorter one an event set meanwhile; flush calls in between join the wait instead of retrying, and calls during a write join it), and after 3 failed attempts the batch is dropped with an error. At 5 000 unwritten events (the batch being written included) a new security event replaces the oldest queued `API_ACCESS` record, never one from the batch being written, and a new access record is dropped; the first drop is warned about at once and the total after the next flush, so a stuck database or a flood cannot grow memory. `AuditLogService.close` stops accepting events (a request still running after the shutdown drain can no longer queue one against the closing database), writes what is left with the same retries, and returns how many events were never written (dropped for a full or closed queue, dropped after failed writes, and what is left), only once no write is running (while closing, a pass asked for during a write is driven by `close` itself, never started behind it); shutdown calls it after the HTTP server and realtime gateway stop and before the database closes. Before any pending migration runs on an existing database, it is copied with `VACUUM INTO` to `<DATA_DIR>/backups/database-<time>-<reason>.sqlite` (the newest 3 are kept; each is a full copy, about the size of the database). A database created before this (tables but no `schema_migrations` rows) is backed up and renamed (`renameColumns`, now only for this case), brought to the baseline and recorded at it only; later migrations then run on it like on any database, so their data-preserving steps (a rename, a backfill) are not skipped. - Tracker scrapes are batched (`services/media-load/src/scrape/scrape-batcher.ts`, in the media-load service below). Requests made within 50 ms of each other share one multi-hash scrape per tracker group: up to 70 hashes in one UDP packet and 20 per HTTP request (about 1,400 URL characters).     - `docker-compose.yml` mounts the downloads folder (`DOWNLOADS_HOST_PATH`) on `miauflix-services` at the backend's old path `/usr/src/app/downloads`, and no longer on `miauflix`. The backend keeps `DOWNLOAD_PATH` to push it.

  - Transfer statistics and verified pieces (contract `media-load` 1.1; calling these on a 1.0 service fails with `unsupported`):
    - Every second the service counts each loaded torrent's peers. Every 5 seconds the bytes it received and uploaded since the previous window become its speeds (the window average) and are added to the new `storage` columns `totalDownloaded` and `totalUploaded` (lifetime totals, unverified and duplicate bytes included). The sample (speeds and the average peer count) goes to the new `transfer_sample` table, except when nothing moved and no peer was connected. Samples older than a day are pruned once a minute and leave with their storage. Migration 2 adds the columns (0 for existing rows) and the table.
    - `storageInventory` items gain `transfer`: the last window's `downloadSpeed`, `uploadSpeed` and `peers` (0 when the torrent is not loaded) and the totals. `transferHistory({ sourceId, since? })` returns a source's samples, oldest first.
    - The event `piecesChanged` (filter `{ sourceIds? }`) reports verified pieces, batched to at most once a second per source: either `added` (the pieces verified since the previous update) or `bitfield` (the whole bitfield, base64, most significant bit first), whichever is smaller as JSON. A whole bitfield also follows lost pieces (reclaims) and a removed storage (`totalPieces` 0, empty bitfield). `storageBitfields({ sourceIds })` returns the current bitfields to start from. Every write of a storage's bitfield, whatever its cause, feeds the updates (`StorageRepository.onBitfield`).
    - The player's seek bar draws three layers: the track (`#555`), the downloaded stretches of the played file (`#bbb`) and the watched part (brand red). The backend's `PlaybackPiecesService` mirrors the verified pieces of every source with a live playback session (`piecesChanged`, started from `storageBitfields` and asked again after a resync). Every second it works out each session's file ranges: each verified piece clipped to the file, in thousandths of the file, rounded outwards and merged where they touch, so a message holds at most 500 ranges. It sends them over the realtime socket only when they changed, as `{ type: 'playback-pieces', playbackId, ranges: [[start, end], …] }`, to the tabs of the session that started the playback, and replays the latest ranges to a tab that connects mid-playback. Until the stream resolves the played file, the source's largest file is used. Ranges are in bytes while the bar is in time, so with variable bitrate a stretch is placed approximately. Against a 1.0 media-load nothing is sent and the bar keeps its old light gray. `PlayerControls` sets the layers as an inline style (`seekTrackBackground`), so values that change every second do not each add a styled-components class. The Storybook story `Home/Player controls › Downloaded pieces` shows the stretches growing.
  - `services/media-load/scripts/runtime-bench.ts` compares Bun and Node: a 512 MB local seed → leech with the encrypted store, then 60 s of the public Debian swarm, reporting throughput, CPU time and RSS. The load test also reports the transfer fields, the history and the piece updates.
  - Storage the backend recorded before this change is handed to the service once (phase 4 of the plan).
    - The ungated calls `importStatus`, `importStorage({ items })` and `completeImport` carry it. Each item is a source descriptor with its storage row, files and claims; dates are ISO strings and the bitfield is base64.
    - Until `completeImport`, the service reports `configuring` (message "Waiting for the host to import its storage") and refuses engine calls. No storage can be created that the import would then skip.
    - The service accepts source directories directly under `DOWNLOAD_PATH` or the service's optional `MEDIA_LOAD_LEGACY_DOWNLOAD_PATH` mount. It writes each source in one transaction, skips sources it already stores, drops playback claims and resets `activeStreams`. `completeImport` seals writes before adoption, then records success after the engine adopts the downloads. If adoption fails, the backend retries it without resending rows.
    - The backend runs `createStorageHandoff(db)` (`backend/src/services/media-load/storage-handoff.ts`) from the new `RemoteService.afterConfigure` hook, which runs after every accepted configuration delivery without delaying it.
    - The handoff sends the `storage`, `storage_file` and `storage_file_claim` rows in batches of up to 50 within the 16 MiB WebSocket limit. It skips rows whose source no longer exists and retries transient failures after 30 seconds. If one source exceeds the frame limit on its own, the backend logs its source ID and leaves the import incomplete, with its original files and records preserved. A fresh install completes an empty import.
    - The backend's rows are kept; a later release drops the tables.
- The backend runs on Bun 1.4 (`bun --env-file=../.env src/app.ts`; `dev` adds `--watch`) instead of Node.js with the ts-node loader, which is removed with `babel.config.js` and `jest.config.js`. The image (`Dockerfile`) is based on `oven/bun:1.4.0` and runs `backend/src/app.ts`: there is no backend `build` script any more, because `bun build` compiles modules imported through tsconfig `paths` with standard decorators instead of the legacy ones TypeORM needs. Details and Bun's differences are in `docs/development/bun-compatibility.md`.
  - `Bun.serve` replaces `@hono/node-server` (`serveStatic` and `getConnInfo` from `hono/bun`), with `idleTimeout: 255` since Bun closes idle connections after 10 s by default. Shutdown awaits `server.stop()`.
  - The realtime gateway uses Bun's WebSockets instead of `ws` (`RealtimeGateway.handles()`, `upgrade()` and `websocket`, still at most 64 KiB per message). A refused origin gets a 403 response instead of a dropped socket. Remote services use the global `WebSocket`.
  - `Bun.password` replaces `bcrypt` and verifies existing hashes. Bun pre-hashes passwords longer than 72 bytes where `bcrypt` truncated them, so a failed check retries with the first 72 bytes and such accounts still sign in.
  - `BackgroundJob.status`, `MediaListItem.mediaType`, `Notification.type` and `StorageFileClaim.kind` declare `type: 'varchar'`: Bun records a column typed with a type alias as `Object`, which TypeORM rejects. The schema is unchanged.
  - `parseResponseBody` reads a body once, as text, then tries JSON. A body without `content-type` that was not JSON used to be read twice, which throws.
  - Backend tests run with `bun test --isolate` (about 6 s). `backend/src/__test-utils__/bun-jest.preload.ts` keeps the Jest API they use: `src/__mocks__` manual mocks applied by module name, top-level `jest.mock('module')`/`jest.unmock()` applied before the test file loads, automatic mocks, `requireActual`/`requireMock`/`mocked`, and `@sinonjs/fake-timers` with the async timer methods. Types still come from `@types/jest`. `backend-e2e` (still Jest) now declares the `@babel/preset-env` its Jest config loads, which it used to get from the backend. The e2e development image (`backend-e2e/docker/backend.dev.Dockerfile`) and the VS Code debug configuration now run the backend with Bun too; both still used Node and the removed `loader.js`.
  - The client types (`build:client`) build with Node's types and a stub of the `bun` module (`backend/client-types/bun`), since `dts-bundle-generator` fails on `bun-types`.

### Bug fixes

- TV pairing: with `TV_PAIRING_ADDRESSES` unset, the configuration returns `''` (empty values skip the transform), and `TvPairingService.configuredAddresses()` called `.map` on it, so every announcement failed. Anything but a list now counts as unset, and the detected addresses are announced.
- **Probes of releases with attached fonts**: `AudioPlaybackService.probe` dumped every stream's `extradata` (`-show_data`), and Matroska exposes attachments as streams whose extradata is the file, so one 600 KB font made 2.6 MB of output, over the 1 MB cap; ffprobe was killed (`ffprobe exited with null`) and the session kept direct delivery without duration, audio tracks or credits marker. Streams are now listed without data, and a second ffprobe dumps only `v:0`'s extradata (all that is read from it). The cap and the 45 s timeout now name themselves in the error detail. Stored probes keep the same shape; failed probes were never stored. **Anime credits chapters**: `explicitCreditsStart` became `explicitCredits(probe, duration)`: it also accepts `Ending`, `ED`, `ED1`, `Ending Song/Theme` and `Outro`, sorts chapters by start, and ignores credits chapters in the first half of the video (opening credits). When a chapter other than credits or a preview/eyecatch/logo/end card follows the credits, its start is the new `PlaybackDelivery.creditsEndSeconds` and the credits no longer end the episode. **Skip intro**: `explicitIntro(probe, duration)` takes the first `Intro`/`Opening` (`Song`/`Theme`/`Credits`/`Titles`)/`OP`/`OP1`/`Title Sequence`/`Main Titles` chapter starting in the first half, ending at the next chapter that is not part of the opening; openings over 5 minutes, without a following chapter or reaching the end are ignored. The delivery exposes `introStartSeconds`/`introEndSeconds`, and `PlayerView` shows a bottom-right "Skip intro" button (no countdown) until the last second of the opening, seeking through the new shared `seekTo`. The prompts ("Skip intro", "Skip credits", next episode) are now rendered inside `PlayerControls` through a `prompts` prop, so the remote reaches them: they form a level between the video and the seek bar, and when a focused prompt disappears the focus returns to the video. The focused "Skip intro" fills white (`:focus`, which Tizen's Chromium 69 supports). **Skip to post-credits**: with `creditsEndSeconds`, `PlayerView` shows "Skip credits (Ns)" / "Watch credits" from the credits start and seeks to `creditsEndSeconds` after 5 s (through the converted-audio seek, now the shared `seekConvertedAudio`, when audio is converted). Seeking into the credits suppresses it, seeking back before them re-arms it. The next-episode fallback countdown starts no earlier than `creditsEndSeconds`, so it does not cover the credits
- `MediaLoadClientService.streamFile` returns media-load's bytes in a response with its own headers. The fetched response's headers are read-only, and Hono copies the context's headers (set by the CORS middleware) onto a returned response, so `/api/stream/:token` failed with `TypeError: immutable` (HTTP 500) whenever the request carried an `Origin`.
- An episode's first play resolves the torrent files of its two best unmatched candidates side by side (`SourceService.getSourcesForEpisodeWithOnDemandSearch`), and `SourceMetadataFileService.getPlaybackTorrentMetadataFile` no longer queues playback lookups behind each other (still at most two at once), so a slow swarm costs one 15-second timeout instead of one per candidate.
- QR sign-in approval (`/auth/qr/:approvalToken`) works again since profiles: it only looked at the profile chosen in this app run, which a newly opened tab (the QR link) never has and which signing in on that page does not set, so it kept asking to sign in. It now approves with the chosen profile, else the device's only profile (including the one just signed in), and asks **Who is approving?** when several profiles are signed in and none is chosen. A refused approval session removes only that profile instead of every profile on the device.
- Live Plushies on the TVs, starting with Who's watching: `liveAvatarsSupported({ onTv: true })` lets a page draw live on the Tizen build when the TV's WebGL is drawn by a GPU (the 2020 TU8072 has WebGL 2 on a Mali-TDVX); the picture uploads still need a browser. Home's sidebar avatar is now a live Plushie on every device, drawn once and not animated (the viewer redraws only on a change): animated, it took Home on the TU8072 from 59 to 54 frames a second at rest and from about 48 to 41 while moving through rows, with half again as many frames over 50 ms; still, it measures the same as the picture (59 at rest, 48–49 moving). The profile panel's avatar remains a picture. three.js's `WebGLRenderer` needs `WeakRef` and `FinalizationRegistry` (Chromium 84), so the Tizen startup polyfills them: references stay strong and nothing is finalized, which only means objects never disposed are freed when their renderer is. On the TU8072, one animated Plushie draws at about 33 frames a second (median frame 17 ms, 95th percentile 58 ms). The editor, which always drew live, had failed on the TVs on the same missing built-ins. A Plushie that cannot be drawn now logs why (`The Plushie could not be drawn`) before falling back to its picture.
- Button layouts on the 2020 TVs (Tizen 5.5, Chromium 69). Chromium before 83 cannot lay out a `<button>` as a grid, and lays out a flex button's children in an inner box that takes the button's `align-items`. The sidebar's profile panel rows were grid buttons, so each icon's `width: 100%` made it about 300px square and the panel grew to about 1750px, running off the top of the screen; the notifications panel's rows and the episode rows (also grid buttons) had the same problem. They are now flex rows with fixed-size icons and posters. In the profile editor, the shape and picture tiles (`flex-direction: column; align-items: center`) shrank their pictures to the label's width (a fabric swatch was 28–62px wide instead of 120px); they now stretch and centre the label with `text-align`.
- A source that failed during playback stopped downloading only when the playback ended. `PlaybackSessionService.failOver` moved the viewers to a new session but kept their `watched` claim (owner `user:<userId>:<playable>`) on the failed source, so media-load went on downloading it greedily next to the replacement; on the VPS a 4K source took about 5 MB/s of the 20 MB/s available after it had been dropped. Fail-over now releases that claim (`releaseClaims(sourceId, ownerKey, 'watched')`, once per viewer), and media-load detaches the torrent once nothing else holds it. What was downloaded stays on disk.
- Storage pressure counted downloads nobody claimed at their full size. Every download reserves its whole file (`reservedBytes`) before it starts, and storage is charged `MAX(allocatedBytes, reservedBytes)`, but the reservation stayed after its claims were gone: a warmup or preload that fetched a few MB of a 13 GB torrent kept charging 13 GB. On the VPS such reservations added about 180 GB to the 100 GB actually on disk, so starting a 39 GB 4K source evicted 22 stored downloads. media-load now releases a storage's reservation (`StorageService.releaseReservation`, measuring its allocation first) when its torrent is detached because nothing claims or streams it, and a new claim reserves again before it downloads. Media-load migration 3 clears the reservation of existing storage with no claim and no active stream where it exceeds the allocation
- Audio inspection of a playing source is retried after 5 and 15 seconds when it fails (not for a 422, which a retry cannot change), while the playback session is still live, and the embedded subtitle probe is tried once more after 3 seconds (not for speculative probes). Both used to give up at the first failure, which on the VPS hit all four probes of a source playback had just switched to, leaving audio unconverted and embedded subtitles unlisted. FFmpeg's stderr was discarded; the last 2 KB now goes into the logs with the failure (`stderr-tail.ts`; `AudioPlaybackError.detail`, never sent to the client)
- Unexpected errors reaching the backend's error handler are logged with the request method, path (long token-like segments masked as `:token`) and stack, instead of only the message; a `TypeError: immutable` seen twice on the VPS during a source switch could not be traced without them
- The services container's fallback access check on the downloads folder (run when changing its owner fails) skips symbolic links, as `chown -R` does: `-d`/`-f` followed them, so a stray link to something read-only stopped every service from starting. media-load never creates links there.

## 2026-11-03 v0.1.0 Samsung TV support, smarter sources, smoother playback, and better reliability

### Features

- Source website traffic moves from the backend to the Bun sources service (`services/sources`, port 3003), using the shared service contract and configuration protocol. The service normalizes candidates, validates hashes, merges trackers and returns incremental search results. Episode searches fall back from IMDb to episode and paginated season queries, so older episodes and season packs are searched beyond a site's newest-results listing.
- Runtime provider management (sources contract 1.1): admins can enable, disable and reorder providers, override per-provider daily and per-minute request budgets, test a provider, and add, refresh or remove provider repositories (JSON manifests, 256 KB cap, refreshed daily; the built-in `builtin:miauflix` repository cannot be removed and a repository never overwrites a provider owned by another one). Provider settings are sealed at rest and password-type values are masked. The backend exposes this under admin-only `/api/sources`, and the frontend adds Settings → Sources. Repository entries of kind `http` are stored but only run once that provider type ships.
- Engine compatibility with community definitions (found by trying [dreulavelle/Prowlarr-Indexers `Custom`](https://github.com/dreulavelle/Prowlarr-Indexers/tree/main/Custom), a set of aggregator definitions that all search by IMDb id): the short `caps.categories` form, JSONPath roots (`$.data.items`) in JSON selectors, namespaced XML selectors (`torznab|attr[name=infohash]`), and no CSS check on selectors of JSON definitions. Most of those definitions need a debrid account or a self-hosted instance, so a `torrentio.yml` for the public Torrentio addon was added to `maury91/miauflix-indexers` (one request by IMDb id and season/episode returns episodes and season packs); it is one of the built-in providers, switched on.
- The indexer picker's filters now describe indexers that need an account too: what their definition says they can do (IMDb search, movies, TV, anime) is recorded even though they cannot be installed, so IMDb search with Public only off lists the 244 definitions that declare it (4 of them public) instead of only the ones we can run. Their rows say why they cannot be added and still show what they support. Stored rows are re-read from the cached definitions once, without downloading anything.
- **No indexer-specific code in the repository.** The native YTS, EZTV and TheRARBG providers, their recorded fixtures, mirror discovery, the site mocks and the `yts-sanitizer` and `therarbg-sanitizer` packages are removed, along with the `YTS_API_URL` and `THE_RARBG_API_URL` settings. Every indexer is a Cardigann definition fetched at runtime. By default that is Prowlarr's `definitions/v11` (YTS among others) plus `maury91/miauflix-indexers`, a separate repository holding the definitions Prowlarr lacks or that do not search by IMDb id (EZTV's JSON API, TheRARBG by title and by IMDb id). A fresh install enables TheRARBG (IMDb), YTS, EZTV (API), Torrentio and TheRARBG (title), and lists Nyaa, EZTV and The Pirate Bay switched off; migration removes the old native provider rows and their usage. A source's own description is shown on its row (`ProviderView.description`), and the backend E2E suite now uses a generic indexer mock with its own test definitions, loaded through the new `SOURCES_PRELOAD_PROVIDERS` startup setting (`<definition id>@<source URL>` entries).
- Jackett Cardigann engine (sources contract 1.2): the sources service runs public Jackett YAML definitions natively, without Jackett. Definitions are fetched at runtime from the configured definition sources (see below; Jackett's are GPL-2.0, so they are never bundled), cached in the service database and kept current by the hourly sync. The supported subset covers Go templates (`if`/`else`/`range`, `or`/`and`/`eq`/`ne`/`not`/`re_replace`/`join`), the usual text, date and size filters, and HTML, JSON (including nested rows and `..` parent access) and XML selectors. Definitions that need an account, use an unsupported filter or template feature, or are malformed are rejected at install time. They remain visible in the indexer picker with the reason they cannot be added, unless excluded by the Public only or Hide unsupported filters. Results that only offer a `.torrent` link or a details page are resolved to a hash by reading the best-seeded eight per search; the rest are dropped. Three public indexers (Nyaa, EZTV, The Pirate Bay) are listed in the built-in repository, disabled; enabling one fetches its definition.
- Torznab client: add a Jackett or Prowlarr endpoint with its URL and API key (sealed at rest). Capabilities come from `t=caps` (cached 24 h, with defaults when unreachable); IMDb searches try `tt…` first and fall back to digits once.
- The Jackett definition list is synced into the sources service database every hour (`CARDIGANN_SYNC_INTERVAL_MINUTES`, default 60; the first run starts shortly after the service is configured, and failed runs retry after 5 minutes). For GitHub-hosted definitions a run uses git (a shallow, sparse, blob-less clone of the definitions folder in the service's data directory; `git` is installed in the service images): one fetch reports which files changed and one checkout downloads only those in a single pack. Measured against Jackett's repository, the first sync takes about 4 seconds and a run with no changes about 1 second, where one request per file took over 35 seconds. If git is unavailable or cannot reach GitHub, a run falls back to listing the upstream tree through GitHub's trees API and downloading the files one by one (set `SOURCES_USE_GIT=false` to always do so). That listing is compact and not capped at 1,000 files, unlike the contents API and compares each file's sha with what it stored: an unchanged tree sha downloads nothing, otherwise only added or changed definitions are downloaded again (6 at a time) and removed ones are dropped, with the change counts kept (`lastChange`). Sources without per-file versions (`<url>/index.json`) are re-read daily instead. Each definition is read once into a `cardigann_index` table (name, language, type, IMDb/TMDB/TVDB search, movies, TV, anime, FlareSolverr, supported or why not), and installed indexers pick up their new definition automatically. A manual Check for updates starts a run at once (sources contract 1.3).
- The indexer definitions come from a configurable list of sources, `CARDIGANN_DEFINITION_SOURCES` (GitHub folder URLs, as `…/tree/<ref>/<path>` or the raw form, separated by spaces or commas; any other http(s) folder that serves an `index.json` also works). The default is Prowlarr's `definitions/v11`: it mirrors Jackett's definitions without the trackers Prowlarr blocks (TheRARBG and TorrentGalaxy are not in it), so the built-in entries are now Nyaa, EZTV and The Pirate Bay from Prowlarr, and the earlier Jackett built-ins that nobody touched are removed. Adding Jackett's folder (`https://github.com/Jackett/Jackett/tree/master/src/Jackett.Common/Definitions`) offers both, and an indexer that exists in several sources is listed once per source, with a Source filter and each copy installable on its own (`prowlarr-<id>`, `jackett-<id>`). Each source has its own clone, sync status and error; removing a source stops offering its indexers while ones already installed keep working from their cached definition. Existing data is migrated: cached definitions and the catalog keep their Jackett origin.
- Regular expressions in definitions are read as Go/.NET syntax: inline flags such as `(?i)` and `(?s)` and `(?P<name>` groups are translated for JavaScript (a community EZTV definition failed on `(?i)`).
- Two more Cardigann engine fixes from testing real definitions: a bare number in a size field (what JSON APIs return) is a count of bytes, not kilobytes (YTS sizes were read 1,024 times too large), and a mode's own parameter list is authoritative, so an ID-only definition such as an API with no text search is no longer offered text queries.
- Found by running Jackett's real TheRARBG definition against the live site: the Cardigann engine now reads Unix timestamps (seconds or milliseconds) as dates, applies the row-level `andmatch` filter (rows must contain every search keyword) and passes a site's `Retry-After` to the provider's pause on HTTP 429.
- The indexer picker filters and pages on the server: IMDb search, TMDB search, TVDB search, Movies, TV, Anime, Public only and Hide unsupported, plus a text search on the name. It opens with IMDb search and Public only on, loads 40 at a time as the end of the list comes into view (or with Show more), and shows when the list was last updated, what changed, and the progress of a running sync. Indexers that cannot be used (accounts, unsupported features) say why and cannot be added.
- Settings → Sources can browse the Jackett definition list, add an indexer, add a Torznab endpoint and remove providers the admin added (kept in a `local:user` repository that appears only while it has providers).
- The sources planner owns provider budgets, request limiting, cooldowns, query caching and search memory. Its VPN guard protects provider and metadata-cache website requests. The backend retains candidate persistence, episode-file matching, WebTorrent metadata, tracker stats, notifications and playback; provider metadata-file URLs cross the boundary only as encrypted references.
- Movie search summaries persist provider coverage, completion and the next retry time. An append-only data migration resets search scheduling for the new planner while keeping existing movies, sources and associations. On-demand movie searches keep saving later results after the caller's response timeout.
- Local development starts source search with `npm run start:sources` (or `npm run start:sources:watch`), and `npm run dev` starts it with the backend, frontend, catalog and lists. Docker's combined services image and its healthcheck include port 3003; the standalone `miauflix-sources` image and development compose service use the same workspace. The backend connects through `SOURCES_SERVICE_URL`, including the shared VPN network and offline E2E stack.

- The compose files combine: `docker-compose.yml` (the former `docker-compose.quickstart.yml`, prebuilt images) is the base of every deployment, and each feature is a file listed after it in `COMPOSE_FILE` (the base must come first, the features in any order): `docker-compose.vpn.yml` (NordVPN), `docker-compose.https.yml` (Caddy), `docker-compose.flaresolverr.yml`, `docker-compose.tracing.yml` (Jaeger) and `docker-compose.build.yml` (build the images from the checkout, running Miauflix as your user so it can read the mounted `.env`). FlareSolverr and Jaeger move into the VPN's network when the VPN file is listed. Image tags follow `MIAUFLIX_VERSION` and `MIAUFLIX_IMAGE_NAMESPACE`. `npm run start:backend:docker:prod` and `npm run config-only:docker` use the `COMPOSE_FILE` from `.env`, or build from source with FlareSolverr, tracing and (with `NORDVPN_PRIVATE_KEY`) the VPN. **Breaking for source-built deployments:** `docker-compose.novpn.yml`, `docker-compose.prod.yml` and the nginx/certbot services are gone (Caddy replaces them), the catalog, list service and Bunqueue run in one `miauflix-services` container, data lives in Docker volumes instead of `./data`, and the backend listens on port 3000 instead of 5000. `docs/setup/docker-setup.md#moving-from-the-old-source-built-stack` copies the data over. The compose files no longer pass `JWT_SECRET`, `STREAM_TOKEN_SECRET`, `STREAM_KEY_SALT` and `SOURCE_SECURITY_KEY` (the old `docker-compose.https.yml` did). Secrets given through the environment are never saved to `config.json`, so a deployment that set them in `.env` must keep passing them, or Miauflix generates new ones and can no longer read its encrypted data, see `docs/setup/docker-setup.md#secrets-set-in-env`. `docs/setup/ssl-certificates.md` is gone: HTTPS is covered in `docs/setup/docker-setup.md#https-with-a-domain`

- The prebuilt-image deployments (`docker-compose.yml` without `docker-compose.build.yml`) update themselves: they run [Watchtower](https://watchtower.nickfedor.com/) (the maintained fork, the original `containrrr/watchtower` is archived), which checks every day at 4:00 for a new image of the tag in use and recreates only the Miauflix containers, removing the replaced images. `WATCHTOWER_SCHEDULE` changes the time. It needs the Docker socket
- `scripts/update.sh` updates a prebuilt-image deployment right away: it pulls the images, recreates the containers that changed and waits until every container is running and the health-checked ones are healthy (`HEALTH_TIMEOUT`, 6 minutes by default, counted from when the containers start being recreated). It then removes only the images it replaced, leaving other projects' unused images alone. `--files` first downloads the newest compose files and `Caddyfile` the deployment already has (from `MIAUFLIX_FILES_REF`, `main` by default): it changes nothing if any download fails, keeps each replaced file as `<file>.<date>-<time>.bak`, and recreates Caddy when the `Caddyfile` changed (on the next run too, if this one fails before Caddy is recreated). `MIAUFLIX_LISTEN_ADDRESS` in `.env` (for example `0.0.0.0`) opens Miauflix to the local network, so it no longer takes an edit to `docker-compose.yml` or `docker-compose.vpn.yml` that `--files` would replace, see `docs/setup/docker-setup.md#updating-miauflix`
- Fake sources are remembered: as soon as a source's file list is known (a downloaded torrent file, a resolved layout, or a playback attempt) it is judged by whether video makes up most of its bytes, and a fake (an `.exe`, an archive, or a small sample beside one) is stored as such and never picked again. Sources are checked ahead of Watch: browsing or opening a title with no verified source queues a background check of its candidates, one torrent at a time with a timeout, without downloading any payload. A data migration judges every source whose file list is already known
- Movies and episodes report whether a playable source exists: movie details and season episodes include `sourceAvailability` (`available`, `pending` or `unavailable`), and changes are pushed live over the realtime connection (`source-availability`), only to the clients showing or focusing that title. The details and browse badges show a "No source" icon instead of the quality, and episodes are marked "No source available", once every source found proved fake
- The player moves on by itself when a source fails and shows "Trying source N of M" while it works through the candidates (pushed live as `source-attempt` while a session is created). Each retry sends the sources that already failed in this browser (`avoidSourceIds`), so the backend picks a different one. When a movie has no source at all (none found, or every one proved fake), the **Watch Now** button on its details becomes **Notify Me**, and turns back once a real source is found. Once every source is exhausted during playback, the player says there is no source for the title and offers **Notify me**, which sends a notification as soon as a real source is found. A user can have up to 200 pending requests, for titles the catalog knows. Requests are re-checked in the background every 6 hours (every pending request, not only the 50 oldest, and a title whose check fails doesn't stop the others), and an episode's matches that are not verified yet are queued for a check

### Improvements

- The TV's Home hero backdrop is sized for the TV, and sharpens while you rest on a title. It used a `w780` backdrop on every TV, which a 2023 QCQ80 stretched to the hero's 1344 pixels. Now the backdrop shown while moving and the one shown once the selection rests are each the smallest size that covers the hero (70% of the app's width), up to what the TV's generation paints smoothly (`frontend/src/shared/config/tv-profile.ts`): 2023 and newer TVs, dated by their model code (`webapis.productinfo.getModelCode()`, `23_…`) or else their browser version, get `w1280` while moving and the `original` at rest (measured on a QCQ80: 70 ms and 97 ms to decode); older ones `w780` and `w1280`. Once the selection rests, the hero loads the resting backdrop while idle (no key pressed for a second), decoded and ahead of the rows' idle preloads, and crossfades to it; moving on drops it unless it has started. A title whose resting backdrop has loaded shows it at once, and details uses it too. `MIAUFLIX_TV_HERO_BACKDROP` and `MIAUFLIX_TV_HERO_BACKDROP_RESTING` (`w300`, `w780`, `w1280`, `original` or `auto`) set the sizes when packaging (`docs/setup/samsung-tv.md`)
- Home on the TV: Back on the remote (or Esc) while browsing the rows opens the sidebar, and pressing it again returns to the selected card. Right on the sidebar's bell no longer opens an empty notifications panel when there are no notifications, read or unread
- Playback can be capped by bitrate: a playback session's `preferences.maxBitrateKbps` (500 to 1,000,000) is the highest average bitrate the client's connection sustains. A movie's sources are estimated from their size and the movie's runtime: the ones within the cap keep their ranking and are tried first, then the rest from the leanest, so a movie with nothing under the cap still plays. A finished download over the cap no longer wins over a leaner torrent. Episodes are capped too, against the show's typical episode length (TMDB's shortest episode runtime, stored on the show as `episodeRuntime` on its next details sync) and the size of the episode's own file in the source, so a season pack counts one episode, not the whole season. A file stored by its path inside the provider's release (without the torrent's top folder) is found by that suffix, as playback does, when exactly one file matches; with several matches its size stays unknown. A show without an episode runtime on TMDB stays uncapped, and a source whose file list is unknown keeps its place. A requested quality (rather than `auto`) is matched among the sources within the cap first, so asking for 4K no longer picks a 4K source over the cap when a lighter source fits; over-cap sources are only used when nothing fits The TV app asks for 8 Mbit/s at most: it fetches a stream at about 11 Mbit/s, and a 4K remux (~35 Mbit/s) froze on its first frame for 18 seconds, then played at a third of real time without audio
- On the TV, loading spinners no longer keep the main thread busy: Chromium 69 animates SVG (the spinner icon's own SMIL loop and its CSS spin) on the main thread, a full frame on every display refresh even out of view, so a row still loading far below the screen cost about 10 ms per frame for as long as it loaded. The TV build spins an HTML element instead, which the compositor animates, including the hero's "checking sources" indicator, and a row loading off screen shows no spinner.
- Home no longer re-renders when the backend pushes the focused title's source status or warmup progress (every few hundred milliseconds while a title warms up): the hero and details read it themselves, and the hero ignores warmup progress, which it doesn't show. Rows and the hero no longer re-render when their own promotion and backdrop requests start and finish, and the set of empty lists keeps its identity while it doesn't change, so loading pages no longer re-renders Home. On the TV a single move along a row now takes 42–44 ms of main thread, down from 47–66.
- Home loads its lists from the store instead of from each row: Home names the rows it wants, a middleware keeps the list pages they need (the selected page and the pages beside it) subscribed and releases the rest, and rows only read the cache. Empty lists are left out before their row renders, so no row mounts just to find out it is empty.
- Home on the TV readies the rows below while you're idle: from a second after the last key press, one more row every half second, up to 10 rows below the visible ones. A ready row is fetched, mounted and rendered in full off screen, so moving down finds it ready; it isn't promoted to the backend until it is on screen. Home also scrolls between rows with a CSS transition that the compositor runs, and the rows around the focused one mount, unmount and load once the slide to it has ended, not during it or on every move of a quick run.

  - On the TV the hero's gradients and backdrops, the row list and each row are on layers of their own. The TV rasterizes in software, and repainted the whole hero with every title change and every frame of a backdrop crossfade or a scroll. Row moves went from about 6–10 to about 30 frames per second, and moves between rows from about 15 to about 30.
  - On the TV the hero's shade is drawn with fixed pixel positions instead of `var()` and `calc()`. Chromium 69 resolved those into new values on every restyle, and every CSS rule styled-components inserts restyles the page, so the whole shade was repainted (about 480 ms) each time: ten times while the app started, including on the intro's first beat and as its expansion started.
  - The hero's backdrop image and fade are inline styles instead of a CSS class per backdrop: every class styled-components inserted made the TV restyle the whole page, about 650 ms over a first pass along a row.
  - The TV loads smaller images, as the legacy app did: 300 px cards and 780 px hero backdrops, since it decodes every image it paints (a 780 px card took about 95 ms).
  - Images load ahead while the user isn't moving: every row with data queues its cards and hero backdrops, nearest the selection first. These idle loads start after the intro (as the legacy app preloaded), run one at a time, only when nothing else is loading and no key was pressed in the last second, and aren't decoded.
  - The intro's two "pam" pulses play on the TV. The logo they scale now gets a layer of its own before the audio starts, so the compositor scales it; until then each pulse repainted the whole screen, and the layer GSAP created as it started took about 250 ms to paint, longer than the 50 ms swell. The layer stays for the expansion, as dropping it cost another full-screen repaint. The intro's letters also show (under the identical settled logo) and get their layers before the audio starts: painting them on the first beat, and eight new letter layers as the expansion started, each stalled the TV for about 250 ms.
  - On the TV the intro waits, after Home is ready, until every image on the page has loaded and then for six smooth frames in a row (at most 5 s in all). Images arriving under the intro, and the TV still painting Home, made it repaint large layers (about 250 ms each) during the first beats.
  - The centred logo pulses on the TV while the app loads. The pulse animated the CSS `scale` property, which the TV's Chromium 69 doesn't have, so only its opacity changed; browsers without it now pulse `transform` instead.
- Approving a QR login (from the TV app or any device) on the `/auth/qr/:token` page always failed with 401: the approve and decline calls didn't send the browser's session (`X-Session-Id`). They now do, and an expired session sends the user back to sign in. A request approved, declined or expired meanwhile (409) now shows its current state
- Redesigned the QR approval page: a centered card below the logo, which now stays where the login screen has it on every step (it used to jump to the top-left corner once signed in and cover the heading), the device named in plain words ("Samsung TV", "Chrome on macOS") instead of its raw user agent, a countdown until the code expires, Approve and Decline buttons, and clear screens for approved, declined and expired codes. ### Technical debt

- Releases are cut by the **Release** workflow (Actions tab, on `main`): given a patch/minor/major bump or an exact version and a title, it renames the changelog's Unreleased section to `<date> v<version> <title>`, sets the version in the root `package.json` and `package-lock.json`, commits and tags `v<version>` on `main`, publishes a GitHub release with that section as its notes (marked latest, unless the version is a prerelease such as `1.2.0-rc.1`) and runs the CI Pipeline on the tag, which publishes the images tagged with the version and `latest`. Pushing to a protected `main` needs a `RELEASE_TOKEN` secret holding a token allowed to push to it; the tag pushed with that token starts the CI Pipeline by itself
- The backend talks to the media catalog and the list service over one WebSocket each instead of an HTTP request per call, an SSE status stream, a separate artwork WebSocket and polling every 15 seconds. Contracts in `@miauflix/service-contracts` are TypeScript types, run by the new `@miauflix/contract` (typed clients, reconnect with re-subscription, status pushed on change, Bun and Node servers); payloads are no longer validated with Zod on both ends of every call. `RemoteServiceManager` is gone, and the config store moved to `@miauflix/service-configuration`. The services' HTTP API (`/v1/...`, `/status`, `/configuration*`, the manifest) is replaced by the WebSocket at `/_c`; only `GET /health` remains. Contracts are versioned `major.minor`: minors only add (new methods marked `since`, which fail with `unsupported` on an older service so callers can degrade), and a breaking change goes into a new major that the service implements next to the previous one while the backend adapts to a service one major behind, so the backend and a service one major apart keep working whichever is deployed first. This release is the one exception: the switch from HTTP to WebSocket has no bridge, so deploy the backend and the services of this release together. A service reports `ready` only once it can serve data calls, and the backend retries, with backoff, a live-update subscription the service rejected while it reported ready, so artwork updates cannot stop for good after a configuration change. The services image installs dev dependencies while it builds the shared packages, since its base image sets `NODE_ENV=production`. At boot the backend waits at most 5 seconds for each service to connect, so an unreachable service no longer holds up startup for its request timeout; it is picked up as soon as it comes online. A call or stream whose signal is already aborted is rejected as `cancelled` without reaching the service, and a failing service status callback is reported instead of crashing the service. Minor behaviour changes: syncing a watchlist for a user without a Trakt account is skipped instead of failing and retrying, a list item without any id is skipped instead of failing the page, and the catalog's unused `/v1/catalog/genres` endpoint is gone

- `SourceService`, `PlaybackTargetService` and `RealtimeGateway` take the background jobs, notifications, source availability, source health and search channel they always get as required dependencies, so the code no longer checks for them on every call. This also removes `SourceService.syncMissingSourceFiles`: nothing called it, the `source.metadata` jobs had replaced it, and its own fallback could not run because background jobs are always present
- CI can publish images for any branch: **Run workflow** on the CI Pipeline in the Actions tab tests the chosen branch and pushes all images tagged with the branch name and `sha-<commit>`, leaving `latest` and `edge` untouched. Only collaborators with write access can start it
- Two flaky unit tests are fixed. The season pack streaming test gave up waiting for playback to be released after 20 event-loop turns, while closing the reader's files is real I/O that can take longer on a busy CI runner; it now waits up to two seconds. The player seek test moved the seek slider before the controls had started listening to the video (the session resolves outside `act`), so the slider was still disabled; it now waits for the slider to be enabled

## 2026-10-26 v0.0.2 Streaming reliability and HTTPS fixes

### Bug fix

- Sources are ranked by their streaming score again: it was never calculated (every source scored 0), so playback could pick a weakly seeded 25 GB 4K release over a well-seeded 1080p one. Scores are now computed when a source is stored, when its provider details change and on every seed/peer update, and existing sources are scored once by the first data migration (in a single transaction). Each score is computed from the stored row inside the same transaction as its write, so a stats check and a provider refresh running together can't leave a stale score
- The realtime connection (live playback updates, notifications, search) works behind HTTPS: `docker-compose.https.yml` sets `CORS_ORIGIN` to the domain, since the default only allows `localhost`
- HTTPS and the VPN can be combined: the `Caddyfile` forwards to `MIAUFLIX_UPSTREAM` (`vpn:3000` with `docker-compose.vpn.yml`)
- The player no longer shows a blue rectangle when its controls overlay takes focus; the volume slider uses the same white focus ring as the buttons
- Video no longer buffers constantly behind HTTPS for viewers on a VPN: the `Caddyfile` serves HTTP/1.1 and HTTP/2 only and `docker-compose.https.yml` no longer publishes 443/UDP. Over HTTP/3 both the direct and the audio-converting stream reached the browser at 4–5 Mbit/s; over HTTP/2 they reach about 150 Mbit/s
- Playback no longer fails with "The SourceBuffer is full" when the audio-converting stream arrives faster than it plays: the player limits read-ahead in seconds, but the browser's media buffer is limited in bytes (about 150 MB in Chrome), so 60 s of a high-bitrate file could overflow it. On a full buffer the player now evicts what is behind the playhead, lowers its read-ahead limit (to no less than 10 s), waits for playback and retries, instead of stopping. While paused it waits for playback to resume; if playback runs but neither the playhead nor eviction moves for 8 checks in a row (about 2 s), it reports the error instead of retrying forever

### Technical debt

- Data migrations: a `migration_version` table and `MigrationService` run the append-only list in `backend/src/database/migrations/` once per database, in order, at startup before any service; the streaming score backfill is the first migration

- HTTPS setup: combine HTTPS with the VPN (the VPN steps keep the HTTPS file), why HTTP/3 is off and how to turn it back on; `COMPOSE_FILE` uses `;` on Windows
- The quick start uses the `latest` release images; image tag documentation covers releases
